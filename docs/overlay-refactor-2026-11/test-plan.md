## 1. 目的、范围与不做什么

- 范围：DeepCode 悬浮交互系统重构后的悬浮入口、顶部事件卡片、状态药丸、底部输入系统、隐藏/召回，以及它们与 DSH 事件面、页面真源、系统手势/导航之间的交互。
- 不在范围：DSH 引擎自身功能、通知中心、浏览器宿主、虚拟屏、Shizuku（除非被悬浮层改动直接触碰）。
- 本文的用例是**判据集合**，不是操作脚本。执行时按仓库 §2.1 要求以「目标 + 约束 + 成功标准」编排真实任务（例如让 Agent 自己在设备上完成一次「后台跑任务 → 悬浮球看进度 → 展开卡片 → 进本体确认」的完整链路），**禁止只做单步点击**。

## 2. 测试层次与判据（缺一层即未验收）

| 层 | 守什么 | 手段 | 通过判据 | 失败读法 |
|---|---|---|---|---|
| A 代码层 | 纯逻辑正确性、契约不变量 | Kotlin 单测（`app/src/test`）+ 静态门禁 | 新增/存量测试全绿；门禁绿；新增逻辑有反例用例 | 红 = 代码或契约有问题，不许当噪声 |
| B CDP/JS 层 | 页面↔原生接口、状态语义、跨层数据 | `verify-*.mjs`（CDP）、页面宿主 API 单测、插件单测 | 断言的是状态语义与真实数据，不是「元素存在」 | 绿而 A 轨红 = 接口与实现脱钩 |
| C ADB 用户层 | 真人能否完成同一件事（点得到、看得见、不被遮挡、键盘正常） | `adb shell input tap/swipe/text/keyevent` + `exec-out screencap -p` | 每步有截图；关键动作可重复（≥10 次或按用例规定） | 两层绿而 C 轨失败 = 交互逻辑错/内部没打通 |

补充判据：
- **几何/层级/遮挡/焦点/键盘**这类缺陷 DOM 断言看不见，必须 C 轨人眼判读（仓内坑 50/61 是实锤）。
- **状态语义**（忙/闲/待答/完成/失败）只有 B 轨能证，不能只贴截图。
- 每一层都要有「结论行 + 证据路径」；缺任一层即未验收。

## 5. 手势与冲突（G 系列）

| ID | 场景 | 判据 |
|---|---|---|
| G-01 | 单击 vs 双击 | 单击在双击判定窗口后执行；快速双击不会先展开再进本体 |
| G-02 | 长按 vs 拖动 | 长按时先移动 > slop 不触发长按 |
| G-03 | 白条拖动 vs 正文滚动 | 白条长按上推跟手收成长条，下拉保留40%展开；正文/代码/工具区滚动不误触白条形变，取消或不足距离平滑回位 |
| G-04 | 长条顶部收起 vs 普通拖动 | 非顶区只移动；首次到顶只限位，继续上推先宽容后距离驱动渐淡；不足/取消回弹，终态才联动收输入；快甩不能绕过宽容区 |
| G-05 | 边缘返回手势 vs 细条 | 沿边缘 20 次返回手势中，细条吞掉的次数可接受（阈值由 S6 定，先记录） |

## 7. 性能测试（P 系列）

### 7.1 指标定义与采集方法

| ID | 指标 | 定义 | 采集方法 | 记录格式 |
|---|---|---|---|---|
| P-01 | 卡片展开耗时 | 点击入口 → 首帧稳定 | `Choreographer` 打点（debug 构建）或 `dumpsys gfxinfo` 帧时间 | p50 / p95（ms） |
| P-02 | 卡片收起耗时 | 收起触发 → 窗口移除完成 | 同上 | p50 / p95 |
| P-03 | 操作期掉帧 | 一次 10 连点 + 拖动 3s 中帧时间 > 2×刷新周期的帧数 | `adb shell dumpsys gfxinfo <pkg> framestats` | 帧数 / 总帧数 |
| P-04 | 拖动流畅度 | 持续拖动 3s 的掉帧率 | 同上 | 百分比 |
| P-05 | 事件到可见延迟 | 事件写入 `.live.ndjson` → 屏上出现 | 注入带时间戳事件 + 截图时序对齐 | p50 / p95（ms） |
| P-06 | 空闲 CPU | 无事件60s内同PID/starttime的utime+stime增量，以实际uptime差换算一核100% | `/proc/<pid>/stat`+`/proc/uptime`前后；保原始数据，top只旁证 | ms / 实际秒、一核%及PID范围 |
| P-07 | 常驻内存 | 悬浮层启用后 PSS 增量 | `dumpsys meminfo <pkg>` 前后对比 | MB |
| P-08 | 冷启动开销 | 悬浮层对首屏可见时间的影响 | `scripts/verify-frame-timing.mjs` + 启动分段 | ms |
| P-09 | 长任务稳定性 | 30 分钟连续事件（模拟工具流）后掉帧/内存 | 事件注入 + 周期采样 | 曲线 + 结论 |
| P-10 | 稳态回归 | 跨版本对比同一脚本输出 | `scripts/perf/measure-steady.ps1` | 与基线差值 |

**现成工具（优先复用，不要重写）**：`scripts/perf/measure-steady.ps1`（冷启/稳态 CPU/内存）、`scripts/verify-frame-timing.mjs`（帧间隔/longtask/跨桥/启动分段）。

### 7.2 阈值产生方式（不编数字）

1. Phase 2 第一周先采**现状基线**（旧面板行为）与本重构首版行为各 3 轮（每轮每方向）。
2. 对每个指标记录 p50/p95 与设备/API/版本。
3. 阈值 = 「不低于现状」或「不超过现状 + 明确预算」；由维护者签字后写入本文件（届时才填数字）。
4. 若某指标无法在设备上稳定采集（方差过大），必须写明原因并降级为「趋势观察」，不得伪造稳定判据。

### 7.3 必须避免的假绿

- 不得用 `am start -W` 判定「悬浮层对启动无影响」。
- 不得用「截图看起来不卡」代替帧数据。
- 不得在 `gfxinfo` 未 `reset` 的情况下比较累计帧数。
- 不得在快照刷新期间或应用被冻结时采集。
- 不得只测一种方向/一种主题就宣布性能通过。
