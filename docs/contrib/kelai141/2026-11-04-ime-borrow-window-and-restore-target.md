# 借道 IME 的窗口边界与还原目标（issue #1516 #1517 #1520）

三条 issue 同一处：`android_ui_input` 走 ADBKeyboard 广播时，为了不劫持用户输入法，
会「读 prev → 临时切到本通道 → 广播 → 还原」。窗口边界、兜底选谁、怎样算「同一把输入法」
三件事各自错了一次，症状都落在「用户下一次打字发现输入法被换了」。

## 现象与真因

1. **窗口太大（#1516）**：互斥锁从「读 prev」一直握到「还原」，中间还夹着 `nodeText` 回读
   （4s 超时 ×2）与重试前的 260/320ms 等待。于是并发第二路在 `await previous` 上无超时、
   无回执地静默等待，最长 9 秒级；前一路若卡在设备回填，后面的注入全部无声卡死。
   真因不是「锁太严」，而是**把不碰输入法的动作也算进了临界区**。
2. **兜底取 ROM 顺序第一行（#1517）**：读回值不可用时从 `ime list -s` 取第一行——那是 ROM 的
   枚举顺序，与用户在用谁无关；回执也不报还原到谁，用户无法核对。
3. **自身排除用严格等值（#1520）**：`restorableImeId` 同时接受 `pkg/.Class` 与 `pkg/pkg.Class`，
   但排除本通道用 `line === selfId`。ROM 打全组件名时 DSH 自己成了还原目标——回执写「已还原」，
   实际用户留在 DSH 键盘上。

## 修法

- 锁只包「读 prev → `ime enable/set` → 广播 → 还原」这一窗；回读与重试等待移到锁外——
  回读读的是**聚焦框文本**，与当前 IME 无关，还原之后再读同样成立。
  「还原」必须留在窗内：下一路在窗内读 prev，本路若还没还回去，它会把 DSH 键盘当用户输入法。
- `acquire({ timeoutMs })` 到点抛 `ImeBorrowTimeout`，并且**让位**：超时的那一路要主动
  resolve 自己的队头，否则一条永不 resolve 的队头会把后面每一路都锁死。回执写明等了多久、
  本次未切换未广播。
- 兜底按「用户常用」排序：读回成功时把用户输入法记进进程内偏好表（最近 3 个），兜底优先命中它；
  没有偏好才退回 ROM 顺序。回执写明还原目标 id 与来源。
- 等值比较统一走 `normalizeImeId`（`pkg/pkg.Class` → `pkg/.Class`）；拼进 `ime set` 的
  仍是 ROM 原样字符串（各 ROM 的 `InputMethodInfo.getId()` 形态不一致，改写反而会撞 Unknown id）。

## 判据与负控

原判据读源码文本（`src.includes('needSwitch = prev !== IME_ID')`），改一行注释就失真——
全部换成行为判据：驱动真工具（假 face 提供壳侧回执），只看发了哪些命令、按什么顺序、
跨两路时谁先动、回执写了什么。负控逐条打红（改坏实现后对应用例 FAILED，再改回）：

| 负控 | 打红的用例 |
|---|---|
| 回读重新关进锁 | `#1516 回读在锁外` |
| `acquire` 不带排队预算 | `#1516 排队超时`（工具层） |
| 超时不让位 | `#1516 超时让位`（锁层） |
| 自身排除退回严格等值 | `#1520 全组件名形态的自身排除` + 纯函数用例 |
| 兜底忽略偏好 | `#1517 兜底不取 ROM 顺序第一行` + 排序/解析用例 |
| 回执不写还原目标 | `#1517 回执必须报出还原目标` |
