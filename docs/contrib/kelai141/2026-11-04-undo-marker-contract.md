# UndoGate 标记文件：退避与观察窗的四条静默失效面（issues #1507 #1508 #1514 #1515 #1530）

日期：2026-11-04 · 仓：dsh-mobile-apk · 面：壳侧 Kotlin（`UndoGate`，自动回滚闸门）

## 现象

四条缺陷都表现为「闸门该退避时不退避、该等观察窗时不等」，而**日志里几乎没有痕迹**：

1. 引擎死透且急救 CLI 起不来时，看门狗入口按 5 分钟退避，但 client-plugin 树失败入口仍**每 5 秒**拉起一次回滚（#1507）；
2. arm 文件被截断成 `1700000000` 仍然「合法」，`armedAt` 远在过去 ⇒ 观察窗被**静默跳过**，引擎还没确认健康就回滚（#1508）；
3. attempt 标记内容坏掉时先删文件再返回 `now`：tick1 抑制、tick2 已是 Missing ⇒ 退避只维持**一拍**，坏标记反而让回滚提前（#1514）；
4. `writeAtomicText` 在 `ATOMIC_MOVE` 不受支持（FUSE / emulated 挂载）时没有回退，ARM 分支退化成 `armed=false`、EXECUTE 分支只留一行日志 ⇒ 退避与观察窗**静默失效**；另有父目录未 fsync、硬杀残留 `.tmp` 无人清（#1515）；
5. arm 文件读失败与「内容为空」同形，一次瞬时 IO 抖动就删掉有效记录、观察窗从头重计（#1530）。

## 真因

- **判据用「能不能 parse」代替了「是不是那个东西」**：`toLongOrNull()` 对截断值同样成功，于是「半截」在两侧都被当成有效时间戳。arm 侧后果是跳过观察窗，attempt 侧后果是退避显示「早已过期」。
- **记账点只有一处**：退避的正确性依赖「放行即记账」，而记账写在两个入口中的一个；测试当时只钉住「两个调用点都把 `attemptAt` 传进 decide」，传参不等于记账，于是第二个入口的缺陷在测试全绿时存活。
- **损坏处置把「保守」写成了「删掉」**：删文件 + 返回 now 让「尝试过」的状态在下一拍蒸发，退避窗口随之消失；原子写本身是 `REPLACE_EXISTING`，预删没有任何必要。
- **读失败无法与空内容区分**：`runCatching { readText() }.getOrNull()` 把 IOException 与 `""` 压成同一个值，于是「这一拍读不到」被当成「这条记录坏了」。
- **原子写有第二份实现**：`UndoGate.writeAtomicText` 自己写 temp+fsync+`ATOMIC_MOVE`，而仓内 `AtomicFileReplace` 早已带普通 move 降级；两份实现的差异正好落在「不支持原子 move 的文件系统」这一支上。

## 修法与复验证据

修法（一次改对，不拆小补丁）：

- 标记契约定死：写 `v2:<13 位毫秒>`，读侧校验「13 位 + 全数字 + 落在 `(0, now+WATCH_MS]`」，越界即损坏；arm 与 attempt **共用同一个编解码器**；
- 抽出 `recordAttempt(dir, now, note)`，两个放行出口共用（`onProbeFailureIn` 的 EXECUTE 与 `onClientPluginTreeFailureIn` 的放行）；
- attempt 标记损坏：**不删文件**，退避起点取文件写入时刻（拿不到退回上次观测/本拍），窗口走完才放行；
- arm 标记损坏：保留 #1369 的「删掉 + 重起窗」；arm 标记**读失败**：`ArmMarker.Unreadable`，保留文件、起点取写入时刻（窗口既不重置也不冻结）；
- 写入器统一走 `AtomicFileReplace`（自带降级），降级经 `publish(tmp, target, onDegrade)` **留痕**；`publish` 补父目录 fsync；闸门第一拍清超龄 `..undo-auto-*.tmp`；
- 判据从源码切片换成**真文件 + 计数**：目录版入口（`onProbeFailureIn` / `onClientPluginTreeFailureIn`）注入目录、时钟与叙述落点，用例直接造 0 字节/半截/读失败/写入时刻。

复验（负控必须真红，逐条实测；细节见 PR）：

| 把实现改坏 | 变红的用例 |
|---|---|
| client-plugin 入口去掉记账 | `一次性入口_放行即记账且不得起观察窗`、`client-plugin 入口每退避窗口只放行一次`、`损坏标记不得删除且退避维持整个窗口` |
| attempt 损坏分支恢复删文件 | `损坏标记不得删除且退避维持整个窗口` |
| 编解码器退回 `toLongOrNull()` | `截断与拼接的时间戳一律判损坏`、`半截的尝试标记不得被解析成有效时间`、`内容损坏时删掉并按本拍重起观察窗` |
| arm 读失败当损坏 | `读失败保留记录且不重置观察窗` |
| 去掉降级留痕/残留清理 | `原子发布降级必须留痕且目标保持完整`、`硬杀残留的临时文件只清旧的且只清本类` |

门禁：`testDebugUnitTest` 全量 + `check-code-map` / `check-kotlin-test-count` / `check-release-gates` / `check-kotlin-comments` 全绿（2026-11-04，本地）。

## 教训（可复用）

1. 「可解析」不是「有效」：凡把时间戳/编号写进文件再读回来做判断，判据必须同时管**形状**（宽度/字符集）与**区间**，否则截断文件会把语义翻成反面。
2. 行为判据的门槛是「能不能造出那个形态」：当实现依赖 `Context` 而无法在 JVM 造 0 字节/读失败时，正确做法是把**目录**当参数注入，而不是退回源码文本切片——后者只能证明「写了调用」，证明不了「语义对」。
3. 「保守处置」不等于「删掉证据」：损坏时的保守是「按已知的上界继续退避」，不是「清空状态、下一拍照旧放行」。
