# 原子写收敛到唯一入口（issue #1057）

## 缺陷

仓里有两套「临时文件 + 原子替换」，强弱不一，而弱的那套恰好被用在**用户数据/状态文件**上。

强的一套是 `SnapshotTransaction.writeTextAtomic`：`Files.createTempFile` 唯一名 + flush +
`fd.sync()` + 发布，失败留 `.pre-*` 证据。弱的一套是 `AtomicFileReplace.writeText`：

```kotlin
val tmp = File(parent, target.name + ".tmp")   // 固定名
tmp.writeText(value)                            // 无 fsync
if (publisher(tmp, target)) return
throw IOException(...)                           // 调用点再各自回退成直写
```

两个后果都是可判定的：

1. **固定名互相踩**：两次写同一目标时，后一次写的 `.tmp` 正是前一次要搬走的那一个。并发/重入
   （`NotifyDecisionQueue.compact` 在 `enqueue` 里被同步调用、修复会话的 `save`/`create`）
   会让两轮内容互相污染。
2. **无 fsync 的 tmp+rename 不算原子**：页缓存还没落盘就已经 rename 覆盖了旧目标，掉电/硬杀后
   目标可能是 0 字节或半截。半截文件比「没更新」坏得多——读侧会解析失败或**静默跳过**。

更坏的是调用点的回退：`AtomicFileReplace.publish` 返回 false 时，两处直接 `target.writeText(...)`：

- `RepairConversationStore.atomicWrite`：直写会在崩溃窗口内留下半写 JSON，而 `load` 的容错把
  「解析失败」当成「不存在」——整段会话静默消失（#511 的放大器）。
- `NotifyDecisionQueue.compact`：直写留下的半写行被 `fold` 的 parse 跳过——**用户作答静默丢失**。

「发布失败」本来是「这次没换成，旧值还在」；回退直写把它变成「确定截断目标」。这不是降级，
是把可恢复失败换成了不可恢复的数据损坏。

## 修法

1. `AtomicFileReplace` 升格为**唯一通用入口**：`Files.createTempFile(parent, "." + name + "-", ".tmp")`
   唯一名 + `FileOutputStream` 写完 flush + `fd.sync()` + 发布；发布失败抛 `IOException` 并清掉
   本次临时文件，**目标保持原值**。`publish` 的签名与「ATOMIC_MOVE 失败退一次普通 move」的回退
   保留不动（大量调用点依赖它）。
   - `writeText` / `writeBytes`：文本面与字节面，fsync 只在这一处实现。
   - `publishWritten(tmp, target)`：给必须**流式落盘**的调用方（启动视频，可能几百 MB）——
     调用方负责写完并 flush，本函数补 fsync 再发布，不把整块字节读进内存。
2. **删除直写回退**，改为调用第 1 步的入口（下面「直写回退清单」）。
3. `SnapshotTransaction.writeTextAtomic` **保持独立**：它需要 `validate` 回调、
   `SnapshotFsException` 错误码与 `.pre-*` 留证语义，与通用面不是同一件事。

## 直写回退清单（全仓 grep：`publish` 失败 → `target.writeText`）

| 位置 | 修前形态 | 处置 |
|---|---|---|
| `RepairConversationStore.atomicWrite` | 固定名 `.tmp` + 失败 `target.writeText` | 改走 `AtomicFileReplace.writeText`（+ 注入式 `publish` 参数） |
| `NotifyDecisionQueue.compact` | 固定名 `FILE_NAME+".tmp"` + 失败 `f.writeText(tmp.readText())` | 同上 |
| `AppLanguage.syncDshLocale` | 固定名 `.lang-tmp` + 失败 `file.writeText` | 改走唯一入口（这是引擎真正加载的 patch） |
| `EngineManager.normalizeLegacySinglePointPatch` | 固定名 `.normalize.tmp` + 失败 `target.writeText` | 改走唯一入口 |
| `SnapshotTransaction.writeMarker` | 固定名 `.snapshot-transaction.tmp` + 失败 `target.writeText` | 改走唯一入口（异常语义仍是 `snapshot-marker-write`） |

## 其余固定名 tmp 的处置

一并收敛（写入的是状态/产物，且发布路径本来就是「delete 后 rename」的非原子两步）：
`ConfigTransfer`（导出/导入 settings.yaml）、`EngineManager.writeOnlineSnapshotIdentity`、
`LinuxAssetIO.download`、`LogShare.packTo`、`SplashStore`。

刻意不动：

- `UpdateChecker.publish`：调用点已经在唯一名 staging 文件上、且发布与「generation 失效」串行。
  它的失败是**下载失败**，不落盘任何东西；改成整块读进内存反而会给 300 MB 的 APK 增加一次
  全量拷贝。
- `SnapshotTransaction.ensureBackupFile`（用 `AtomicFileReplace.publish` 发布 `.pre-*` 备份）：
  已有唯一临时名与 fsync，改它只会扩大改动面。
- `FileIncoming` / `PluginMounts` / `SourceMirror` / `SafeMode` / `UndoGate` / `ReverseMigration`
  等：本来就是唯一临时名，其中若干个已自带 fsync 或 `ATOMIC_MOVE`；本轮不扩散。

### 已知的环境噪声（不是本改动的回归）

全量套件在**同一台机器上同时跑别的 gradle 任务**时，`ProcIoTest.drainTimeoutIsNotTheSameShapeAsVacuousOutput`
会偶发判红：该用例的桩进程永不 EOF，靠 `awaitCompletion` 里 `normalDrainMs = 5_000` 的 join
预算把排水线程判成「还活着」，机器被抢占时 5 秒内真的能排空，断言 `vacuous.timedOut` 就翻了。
判据：单独跑该类必绿（已实测 2 次），与本改动无交集（`ProcIo.kt` 不在 diff 里）。本轮全量跑了
三次，第三次（不与任何 gradle 任务并行）2067 例全绿。这条属于既有 flaky，未在本 PR 修——
修它要动 `ProcIo` 的判据口径，是另一件事。

## 判据口味（写死在这里，避免下次又「补一条行为测试」却补不出来）

「失败不直写」对 `RepairConversationStore` / `NotifyDecisionQueue` 曾经**只能**做源码级判据：
生产代码里没有 publisher 注入口，JVM 上打不中「发布失败」这条分支，而回退直写只在那条分支上
才走。本轮按仓内既有惯例（`SnapshotTransaction.writeTextAtomic` 的 `publish` 参数）给这两个
入口加了**默认化**的 `publish` 参数，于是它们也有行为判据了。源码级那两条保留：它们守的是
「实现形状不再长出第二条路径」，行为判据守的是「今天这条路径是对的」，两者不可互相替代。
