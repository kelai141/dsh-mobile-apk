# 壳侧 P2 交互缺陷三连（2026-11-05，issue #1621 / #1612 / #1618）

## 现场

三条都在「用户当场能碰到」的那一层，共同形状是**判据/计时锚错了对象**：

- #1621：NOT_READY 预算按**入队时刻** `ts` 算；重试按钮只做一次 `flush()`，既不改 `ts` 也不把状态
  改回 PENDING。对已超 5 分钟预算的 FAILED 决策，`handleNotReady` 立刻再判 FAIL → 又发一条同样的
  「提交失败」。用户点了「重试」，看到的是**又一条失败**，一次投递尝试都没做（死路）。
- #1612：`showPanel()` 给面板窗口的 flags 只有 `FLAG_NOT_TOUCH_MODAL`（即**可聚焦**，弹输入法需要），
  而全仓没有任何 `KEYCODE_BACK` / `setOnKeyListener` / `dispatchKeyEvent`。BACK 被派发给获得焦点的
  overlay 窗口，视图树无人消费；非 Activity 窗口没有默认回落 ⇒ 事件被丢弃。用户视角：返回键死了。
- #1618：单次 2s × 3 次 = 6s 的重试阶梯，而看门狗 4s 就 `location.reload()`。一次 2.5s 的正常删除
  会先超时、再在第 2 次重试途中被整页刷新 —— 用户丢掉滚动位置与输入框草稿，600ms 后 resume 路径
  又补发第三次。

## 真因

- #1621：**「用户要求重试」与「队列自己的节奏」用了同一个入口**。flush 的语义是「按队列现状再试一次」，
  而重试按钮的语义是「从现在重新计时再试」；共用入口后，重试退化成「再评估一次预算」。
- #1612：**可聚焦窗口的按键必须自己消费**。这个约束在 Android 上是硬性的（Activity 有默认回落，
  overlay 窗口没有），而壳侧此前把它当成「WebView 会处理」。
- #1618：两个独立常量各写各的（`REQUEST_TIMEOUT_MS`/`MAX_ATTEMPTS` 与 `WATCHDOG_MS`），
  没有任何东西把「看门狗必须覆盖完阶梯」这条关系钉住。

## 修法（全部零位移）

- #1621：新增纯函数 `NotifyDecisionQueue.rearm(d, now)`（状态回 pending、ts = now、两个计数归零）与
  入口 `retryFailed(context, eventId, now)`（找到 FAILED/PENDING 那条 → rearm → 落盘）；`NotifyActionReceiver`
  的 `ACTION_RETRY` 分支改为先 `retryFailed` 再走原有的一次 flush。**不加行、不改既有行**。
- #1612：新增 `OverlayPanelBackKey.kt`（纯函数 `consumePanelBack` + `BackKeyPanelLayout`），
  `OverlayPanel.buildUnit()` 里根容器**同行替换** `LinearLayout(svc)` → `BackKeyPanelLayout(svc)`。
  拦截点选**窗口根 View 的 dispatchKeyEvent** 而不是 `setOnKeyListener`：`ViewGroup.dispatchKeyEvent`
  在「自己没焦点、也没有子 View 有焦点」时直接 `return false`，挂在 ViewGroup 上的 OnKeyListener 根本
  不会被调用 —— 面板根是 LinearLayout，子控件轮着拿焦点，那会表现为「有时能返回、有时不能」。
- #1618：`WATCHDOG_MS = MAX_ATTEMPTS * REQUEST_TIMEOUT_MS + 4000`（同行替换 4000）。关系式而不是
  新的魔法数：改阶梯任何一项，看门狗自动跟着走。

## 负控（都真打红过，随后已还原）

- #1621 队列侧：`rearm()` 改回 `ts = d.ts`（= 「重试不重置计时」的原形状）→ `NotifyDecisionQueueRetryTest`
  2 例红（「重排后这条决策必须重新计时」「点重试必须把队列里的那条真的改回待投递」）。
- #1621 接线侧：`retryFailed()` 改回 `mark(context, target, State.PENDING)`（只改状态不重排）→ 1 例红；
  再把接收器的 `retryFailed(...)` 换成 `false`（= 本 issue 的原始形状：只记日志）→ `NotifyActionRetryWiringTest`
  1 例红（队列里那条停在 failed / ts 没动）。
- #1612 规则侧：`consumePanelBack` 去掉 `ACTION_UP` 守卫（按下就收）→ 「一次按压只收一次面板」红。
- #1612 接线侧：面板根改回 `LinearLayout(svc)` → 「面板根容器必须是带返回键拦截的那个类」红；
  同时真类那例也红（证明这一例不是只钉纯函数）。
- #1618：`WATCHDOG_MS` 改回 4000 → `watchdog-ladder.test.mjs` 3 例中 2 例红（阶梯途中被刷新、
  彻底卡死时刷新时刻早于阶梯）。保留的那 1 例是**保住的行为**（慢但成功的删除不被打断），
  修前后都绿 —— 它是「别把真卡死也要有人管一起改掉」的对照面。

## 判据为什么不是源码切片

三条各有一层「跑真东西」的判据：#1621 走真队列文件 + 真接收器类；#1612 构造真的
`BackKeyPanelLayout` 实例把键喂进它的决策口；#1618 用假时钟驱动真实客户端 bundle，看
「重载发生在第几毫秒、那时阶梯走到第几步」。源码切片只出现在「接线存在性」这一层（例如
「面板根必须是这个类」），且每条都配了能让它变红的负控。
