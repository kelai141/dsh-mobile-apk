# #1006 来件投递执行器被 20s 重试占住 / #919 壳侧 export 端点 HEAD 预检未拦

## 现象

- **#1006**：外部分享一个文件进来后，短时间内再分享第二个，第二个要等最长 20s 才开始拷贝。
- **#919**：点「导出会话日志」，页面上什么都看不到（没有下载、没有报错）。

## 真因

### #1006：单线程执行器承载了「等待」，而不是只做 IO

`FileIncoming.ioExecutor` 是 `newSingleThreadExecutor`（0.13.8 #174 引入，目的是让
onCreate 前台零 IO）。但 `processIncomingIntent` / `processIncomingPath` 把
「入待发清单 → 最长 20s 的重试轮询」整段放在这条线程上：

```kotlin
val deadline = System.currentTimeMillis() + 20_000
while (System.currentTimeMillis() < deadline) {
  if (flushPending(context)) return@withIncomingDeliveryAfterSweep
  try { Thread.sleep(4_000) } catch ...
}
```

重试的大部分时间是 `Thread.sleep`，而单线程执行器是**串行队列** ⇒ 后一个来件的拷贝任务
排在前面那 20s 之后。用户视角 = 「第二个文件卡住了，过一会儿才出现」。

### #919 壳侧一半：`isSessionExport` 只认 GET，而插件先发 HEAD

`DownloadSaver.isSessionExport(url, method)` 是 `method == "GET"`。引擎插件在真正发
GET 之前先发 **HEAD 预检**（判断端点是否可用）。HEAD 不命中 ⇒ 落进
`shouldOverrideUrlLoading` 的 `isEngineSource` 分支 ⇒ 交给 WebView 自己导航 ⇒
插件拿到的是导航结果而不是 app 内下载通道 ⇒ 进错误分支。而那个错误弹窗被 Web 侧 CSS 隐藏
⇒ 用户看到「什么也没发生」。

两者叠加：即使 HEAD 被正确拦下，若把 HEAD 也送进 `downloadToDownloads`，一次导出会落
**两份文件**、发两条通知。所以 HEAD 必须与之分流。

## 修法

1. **#1006**：新增 `deliveryRetryExecutor`（cached pool，每次投递一个线程）+ `retryDelivery()`。
   两个入口只做「拷贝 → 记账 → 入待发清单」，随即把「等待受理」交给重试线程，IO 线程立即
   返回处理下一件。重试预算/间隔仍是 20s / 4s（不改用户已验收的策略），且 `retryDelivery`
   在整段里持有 `activeDeliveries`（`finally` 归还）——保留 FX-211.2 那条「划掉应用不得
   丢掉在途来件」的纪律。
2. **#919 壳侧一半**：`isSessionExport` 接受 GET **或 HEAD**；新增
   `isSessionExportPreflight(method)` 与 `probeSessionExport(url)`——后者只发一次
   `HEAD`（`Proxy.NO_PROXY` 直连 + `EngineAuth.attach`，401 自愈换一次），**只读状态码、
   不写盘**，把结果落进 `pushExportResult` 通道。`MainActivity` 里按方法分流：
   HEAD → `probeSessionExport`，GET → `downloadToDownloads`。

Web 侧那半（不要把 error 隐藏）不在本 PR 内。

## 双向判据

新增 `IncomingDeliveryAndExportPreflightTest`（5 条用例），每条都成对：

| 方向 | 用例 |
|---|---|
| 抓缺陷 | HEAD 必须命中拦截判据 / 重试不得跑在单线程 IO 执行器上 / 重试执行器不得也是单线程 |
| 放行例 | 非引擎源、非导出路径、前缀欺骗、POST 一律不命中 / 重试预算与间隔口径不得被改 / 重试不得被删（冷启动补投）/ 预检不得写盘 |

## 负控（三处，全部实测变红）

| 变异 | 失败原文 |
|---|---|
| M1 退回 `method == "GET"`（#919 缺陷形态） | `HEAD 必须命中会话导出判据（否则不会被拦，直接交给 WebView）` |
| M2 把重试循环塞回 io 线程内联（#1006 缺陷形态） | `fun processIncomingIntent( 不得内联 Thread.sleep 重试循环（那会占住单线程）` |
| M3 重试池退化为单线程（看着「搬了」实则没改善） | `重试执行器不得也是单线程（否则等于没搬）` |

## 踩到的坑：行号锚点

`EXECUTION-MAP` 按 `path:line` 引用 `FileIncoming.kt` 与 `DownloadSaver.kt` 共 30+ 处。
把新成员插在文件**中段**会让这些锚点整体位移（本轮实测 13 条 drift）。

两条硬约束叠加后很难受：
- 行号引用**不能**落在表格单元格里带 `#expect`（尾随 `|` 会被当成片段的一部分）；
- 门禁又要求**新出现的**行号引用必须带 `#expect`。

处置：把新增成员全部**移到类尾**，让既有行号零位移；只对语义确实变了的 3 处锚点手工
重指（并把「表格单元格不能带 #expect」这条记在这里，免得下次再试）。
