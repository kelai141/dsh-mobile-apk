# 更新块住进卡片后暴露的三处陷阱（2026-10-29）

主题：引导页「检查更新」区域的两枚按钮包成一张卡片（分支 `feat/guide-update-card`）。
改动本身很小（一个容器 + 一对共享规格函数），但过程中撞到三个**只要把控件搬进新容器就会
复发**的形态。前两条的共同点：旧位置上有对比、搬进新容器后对比消失，而编译、门禁、单测全绿。
第三条是对齐**基准**选错——比"没对齐"更难发现，因为两侧各自都自洽。

## 1. 按钮填充色与卡片底色是同一个 token（`ds_surface`）

- **现象**：把更新块包成卡片后，两枚按钮（检查更新 / 下载）与卡片「融为一体」——按钮的边界
  只剩下文字，看不出可点区域。改动前同样写着 `R.color.ds_surface`，屏幕上却看不出问题。
- **真因**：更新块旧形态直接坐在管理中心的面板底色（`ds_bg`）上，而按钮填充是 `ds_surface`
  ——两者是**不同**的 token，天然有对比。卡片容器用的也是 `ds_surface`，于是按钮填充与它
  父容器**同色**：填充层完全隐形，只剩 `RippleDrawable` 的按压反馈还在。这类缺陷不会在
  任何一层判红：资源名合法、编译通过、圆角与尺寸都对。
- **修法**：按钮填充改用 `ds_button_surface`（浅色 `#E8E8ED` / 暗色 `#343437`）——这套设计里
  专为「按钮面」准备的 token，两套配色下都与 `ds_surface` 有对比。注释写清「为什么不能是
  `ds_surface`」，免得下次有人看着旧值觉得「本来就是这么写的」再改回去。
- **复验证据**：`GuideUpdateCardTokenTest` 的「按钮填充色不得与卡片底色同 token」逐条断言
  `updateBlock()` 内出现 `R.color.ds_button_surface`、**不**出现 `R.color.ds_surface`，并断言
  `values` 与 `values-night` 两套 colors.xml 都定义该 token。受控负控：把填充色改回
  `ds_surface` → 该用例判红；改回即绿。

## 2. 「两处各写一遍恰好一样」不是对齐，是漂移的起点

- **现象**：要求「卡片规格与页面其它卡片一致」时，最省事的写法是把另一处卡片那五条 token
  （底色 / 圆角 / 描边 / 描边宽 / 内边距）照抄进更新块。抄完当场是对的。
- **真因**：抄写不是对齐关系。下次谁调了其中一处（比如把卡片圆角从 12dp 改成 14dp），
  另一处不会跟着变，而**单看任一文件都发现不了**——两个文件各自都「内部一致」。
  这类漂移没有编译期或运行期信号，只能靠人在两个屏幕上比对。
- **修法**：把卡片的外壳规格收成 `DsUi.settingsCardBackground(context)` /
  `DsUi.settingsCardPaddingPx(context)` 两个函数。更新卡只调用它们，规格值本身只写在 DsUi 里，
  「改一处两边一起变」变成结构性事实，不依赖谁记得同步。
- **复验证据**：`GuideUpdateCardTokenTest` 的「卡片外壳规格取自 DsUi 的设置卡这对函数」断言
  卡片体内出现这两个调用点，并**反证**卡片体内不得再出现圆角 / 描边 / 内边距 token
  （自己重写一份就判红）。负控：把卡片改回内联 `roundRect`，该用例判红。

## 3. 对齐基准必须取「对面那一侧的真实来源」，不能取本侧另一处自洽实现

- **现象**：第一版把「与页面其它卡片对齐」理解成「与引导页状态卡对齐」，于是取了
  18dp 圆角 / 24dp 内边距 —— 在本侧内部完全自洽，单测和门禁全绿。但用户的意图是**两个入口**
  （启动页原生卡 vs 设置页 WebView 卡）看起来是同一套设计，而 WebView 那张卡早在 `#860` 就
  改了外壳：`padding: 12px; border-radius: 12px; border: 1px solid; gap: 10px`。
  以本侧另一处为基准，得到的是「本侧内部一致、跨侧不一致」。
- **真因**：对齐是**跨侧关系**，基准必须是关系另一端的事实来源。本侧存在多套各自自洽的
  卡片规格（8dp / 12dp / 18dp 圆角各有用例），任选其一都能自证「一致」——这正是这类
  偏差不会被任何一层判红的原因。
- **修法**：基准改取 `dsh-client-ui-responsive/src/client/dev-section/dev-section.css.ts` 的
  `.dsh-screen-control-card`（#860 起「应用更新」分区用它），并追溯到上游令牌实际取值
  （`packages/client/ui-theme/src/styles/`：`dsw-radius-md: 12px`、`alias-bg-layer-2`、
  `alias-border-l3`）。原生侧新增 `ds_radius_settings_card=12dp` 补上缺失的那一档
  （`ds_radius_sm=8dp` 对应 `dsw-radius-sm`、`ds_radius_md=16dp` 对应 `dsw-radius-lg`，
  中间这一档此前缺位）。文字层级同步取 `.dsh-gs-title`(14px) / `.dsh-gs-desc`(12px, 行高 18px)。
- **复验证据**：`GuideUpdateCardTokenTest` 的「卡片圆角与内边距取 12 这一档而不是近似取整」
  用 `dimenValue()` 从 `dimens.xml` 里**读实际 dp 值**断言等于 `12dp`（不是断言"引用了某个
  token"——引用了却写 14dp 也会绿），并反证不得用 `ds_radius_sm` / `ds_radius_md` /
  `ds_radius_card` 近似。「标题与状态行的字号行高对齐 WebView 卡片的标题与说明」同理钉住
  14sp / 12sp / 1.5 倍行距。

## 可复用结论

1. 把控件搬进新容器时，先问「这个控件原来的对比度来自哪一层底色」。**填充色与父容器底色
   同 token = 隐形**，且这一层没有任何自动化信号。
2. 「与其它卡片对齐」应落成**共享函数**，而不是复制一份数值。可断言的是「谁在读哪个
   token」，不是「两处的魔法数相等」——后者只能靠人眼比对，前者能被单测钉住。
3. 跨侧对齐（原生 vs WebView）的基准只能是对面那一侧的真实来源。本侧总能找到一处
   自洽实现来"证明"一致——那不是对齐，是自证。断言里要读**实际数值**而不是"引用了 token"。
4. JVM 单测里没有 View 树，截图才证得了像素；但**token 的引用关系与实际取值**是源码里的
   事实，在单测里钉它成本最低、复发率也最低。两层各管一半。
