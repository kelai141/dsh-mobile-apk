# #1017 修复助手：配置解析收敛到后台单点，会话落盘移出主线程

## 现象

原生修复助手（`RepairActivity`）打开一次，整份模型配置被完整解析**两遍**，其中一遍在主线程；
会话 JSON 的序列化与落盘也在调用线程（多数是主线程）上做。

## 真因（修前行号）

- `RepairActivity.kt:475-478`：`onCreate` 直接调 `openOrCreateSession()`，函数体第一行是
  `connections = RepairModelConfig.load(applicationContext)` —— **主线程整份解析**。
  `load(context)` 是 `loadDetailed(context).connections`（`RepairModelConfig.kt:56`），
  而 `loadDetailed(context)` 除了解析 YAML 与凭据，还会原子写一次
  `filesDir/repair-model-source.json`（`RepairModelConfig.kt:62-70`）。
- `RepairActivity.kt:151-160`：紧随其后的 worker 里 `connections = loadRepairModels()`
  （`RepairActivity.kt:73-87` → `RepairModelConfig.loadDetailed`）**再完整解析一遍**。
  同一个值、同一次打开，解析两遍。
- `RepairActivity.kt:728`：每轮修复结束的 `runOnUiThread` 里又 `RepairModelConfig.load`，
  主线程第三次解析。
- `RepairActivity.kt:560-580`：`saveCurrentSession()` 在调用线程上
  `JSONArray(history.toString())` + `JSONArray(eventLog.toString())`（整份会话序列化再解析）
  并 `RepairConversationStore.save`（原子写 + 重写 index.json + prune 目录扫描）。
  调用点 `469 / 492 / 505 / 557 / 641 / 700 / 711 / 723 / 1064 / 1206`，
  其中 `469`(beginAutomaticRepair) / `492`(createNewConversation) / `505`(switchConversation) /
  `1064`(模型面板关闭) / `1206`(onDestroy) 都在主线程。

## 修法

1. **配置解析收敛到单点**：删掉只返回候选的窄入口 `RepairModelConfig.load(context)`
   （它正好让调用方「主线程顺手解析一遍 + 后台完整解析一遍」）。现在唯一的 Context 入口是
   `loadDetailed(context)`，且只被后台的 `loadRepairModels()` 调用。
2. **打开会话不再解码配置**：`openOrCreateSession()` 只做会话读写；会话里记下的模型身份/
   推理强度先存进 `pendingIdentity`/`pendingEffort`，等 worker 拿到候选后由
   `restoreSelection()` 落定。**否则恢复会话会静默退回第一个候选**——这是挪走主线程解析时
   最容易漏掉的副作用。
3. **每轮结束的刷新也移出主线程**：`runOnUiThread` 里那次 `RepairModelConfig.load` 改到
   worker 上走同一个 `loadRepairModels()`，UI 线程只做赋值。
4. **会话落盘移出调用线程**：新增 `RepairSessionWriter`（单线程串行写）+
   `RepairSessionJson.copy`（结构深拷贝，代替 `toString()` 再解析）。
   `saveCurrentSession()` 变成「冻结快照 + 提交」，`onDestroy` 显式 `flush()`。

## 顺序语义（为什么不能直接扔线程池）

切会话是「先存旧会话、再加载新会话」。若两笔写盘可并发或乱序，旧快照会后落盘盖掉新快照，
用户看到「切换会话后内容还是上一个会话的」。`RepairSessionWriter` 的契约：

- **同一时刻只有一次写盘**（`writing` 标志；`flush` 超时时若仍在写，直接返回 false，
  绝不在调用线程上抢写）；
- **最新覆盖**：提交之间只保留最后一笔。每笔提交都是提交时刻的完整会话，
  丢掉被顶掉的旧快照是「更新的替换更旧的」，不是丢增量；
- **退出必须 flush**：`onDestroy` 等到落盘；超时在调用线程兜底写完，宁慢不丢；
- **失败隔离**：单笔失败只记账，不阻塞后续快照；`failure` 只描述最近一笔
  （成功一笔即清空，否则一次历史失败会让之后每次 `flush` 恒返回 false，退出判据失效）。

- 让 `flush` 超时后与在途写盘并发（模拟「旧覆盖新」）→ 对应例红。

## 为什么选源码级判据而不是线程断言

本仓 JVM 单测没有 Robolectric（`app/build.gradle.kts` 只有 junit + org.json，且
`unitTests.isReturnDefaultValues = true` 把 `android.*` 打桩成 0/null），拉起 Activity 会直接
拿到空 `filesDir`；而「在后台线程」是**结构**属性，不是时间属性——用时间断言必然不稳定。
故沿用仓内既有先例（`RepairGateTest` / `MainActivityPrivilegeEntryTest` 的
「函数切片 + 名字断言」），判据是「主线程路径上不再出现解码/落盘调用点」。
线程行为本身另用 `RepairSessionWriterTest` 的真线程用例覆盖。
