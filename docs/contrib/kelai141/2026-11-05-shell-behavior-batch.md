# 壳侧行为批（#1592 #1594 #1598 #1599 #1600 #1601 #1605 #1612 #1617 #1618 #1623 #1627 #1628 #1629）

## 这批的共同形态

十几条缺陷单独看都很小，但判据形态是同一个问题：**离线判据要么不存在，要么落在「源码里有这一行」上**。
形态在、语义不对时照样全绿（join 超时写成 0、BACK 判定写成 ACTION_DOWN、槽位校验删掉但测试没等那一帧）。
本轮每一条都先问「撤掉修复，这条用例会不会红」，红不了就重写判据。

## 两条真踩到的坑

### 1. `refresh()` 只排一帧，断言必须等那一帧

`mobile-workspaces.ts` 的 `refresh()` 是 `requestAnimationFrame(() => this.sync())`。第一版 #1628 用例在
`refresh()` 之后立刻读属性，读到的是**旧值**——把取值校验整段删掉，用例照样全绿（负控不红 = 判据没有判别力）。
加 `await h.flush()` 之后负控才真变红（`expected [ 'NaN', 'NaN' ] to deeply equal [ null, null ]`）。

**教训**：负控不红时，先怀疑判据在断言旧状态，而不是怀疑「这条缺陷不影响行为」。

### 2. 停机等待写成 `join()` 会把负控变成挂死

`WorkerJoin` 的负控第一版是「把有界 join 改成无界 join」，结果测试进程直接挂住、CI 看起来像超时。
负控要选**能红且会退出**的形态：改成 `if (false) join(...)`（旧形态 = 只翻标志位就返回），
用例立刻以断言失败退出。

**教训**：负控本身也要能在有界时间内结束，否则它不是证据、是故障。

## 判据怎么落地

- 能抽成纯函数的抽出来直接测：`StagedPull`（长度核对 + 发布）、`WorkerJoin`（有界等待）、`OverlayBackKey`（真值表）。
- 需要 View/Window/Binder 的形态留在 `ShellBehaviorBatchTest` 里做「修复形态在场 + 旧形态不在场」，
  并在注释里写清旧形态为什么错——负控时把实现改回去，这些用例逐条变红。
- 设备面（锁屏审批、通知动作、返回键真实派发）本轮**未做设备验证**，PR 里显式标注。
