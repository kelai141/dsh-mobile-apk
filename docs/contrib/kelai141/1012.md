# 修复助手把「配置树不可读」误报成「未读到可用模型」（#1012）

## 现象

引擎连续两次启动失败后助手被拉起，顶部横幅报「未读到可用模型。可在控制台修好配置后重新读取，也可直接重试引擎。」，
右上角模型选择器与发送键一起变灰。用户按提示去改模型配置——改完还是同样的报错，因为问题不在配置。

## 真因

三处判定各自都「没错」，叠在一起把根因吞掉了：

1. `RepairModelConfig.loadDetailed` 对 `home/.dsh` 整个不存在的情形没有任何专门判定。`readInto`
   对每个文件只报 `missing`，于是「运行时还没解出来」与「用户删了自己的配置」在数据层完全同形——
   两条来源表都是若干条 `missing`，候选数都是 0。
2. `RepairModelNotice.present` 的分支顺序把 `candidateCount == 0` 排在 `!diagnosticsReady` 之前。
   运行时死掉时两者同时成立，更准确的那条原因（诊断也读不到）被归纳句吞掉。
3. `RepairActivity.applyModelState` 用同一个 `modelControlsEnabled` 同时控制模型选择器与发送键。
   0 候选时连发送一起禁用，用户除了退出去没有别的动作。

触发时机是结构性的：助手只在引擎连续两次启动失败后被拉起（`EngineStartFlow.requireNativeRepair`），
而那正是快照最可能还没解完、`home/.dsh` 还不存在的时刻。

## 修法

- **A1（数据层）**：`RepairModelLoad` 新增 `rootMissing`；`loadDetailed` 在 `!dsh.exists()` 时短路，
  只产出一条 `root-missing` 来源，不再伪造五条 `missing`。UI 文案改为指向「运行时还没解出来，
  返回启动页重试引擎」，并在 `statusLabels` 登记 `root-missing`（中英双语）。
- **A2（分支顺序）**：`present` 里根缺失排在 0 候选之前；0 候选且诊断未就绪时把诊断原因拼进正文，
  两句都说，不再让归纳句吞掉更具体的原因。
- **A3（控件与草稿）**：`Presentation` 拆出 `sendEnabled`，0 候选只关模型选择器，不关发送。
  同时修掉配套的吞输入缺陷：`submit()` 原先先 `input.setText("")` 再进 `runAgent()`，
  而 `runAgent` 在无候选时静默 return——用户打的字凭空消失且界面毫无反应。现在「可否发送」
  与「保留草稿」由纯函数 `RepairModelNotice.composer` 一处判定，清空输入只发生在真要发出去之后；
  发不出去时明确告诉用户原因并保留内容。

三条改动都落在同一条判定链上，故合为一个 PR。

## 判定抽成纯函数

`RepairActivity` 是 Activity，JVM 单测实例化不了；凡是要断言 UI 行为的，判定都挪进
`RepairModelNotice`（`present` 的 `sendEnabled`/`rootMissing`、`composer`），Activity 只落结果。
没有新增 .kt 文件。

## 负控（修前必须红）

| 用例 | 修前失败摘要 |
|---|---|
| `RepairModelConfigTest.configTreeRootMissingIsNotReportedAsFiveMissingFiles` | 来源表只有 4 条 `missing`，没有任何 `root-missing` |
| `RepairModelNoticeTest.零候选且诊断读不到时正文必须带上更准确的诊断原因` | 正文只有「未读到可用模型…」，诊断原因被吞 |
| `RepairModelNoticeTest.配置根源缺失时提示指向运行时而不是没模型` | 该参数修前不存在，用例无法编译（结构性缺席） |
| `RepairModelNoticeTest.零候选时发送键不被禁用` | `sendEnabled` 修前不存在，用例无法编译（结构性缺席） |
| `RepairModelNoticeTest.零候选时提交既不发送也不得丢弃草稿` | `composer` 修前不存在，用例无法编译（结构性缺席） |

前两条是行为红（旧代码编译通过、断言失败）；后三条断言的是新判定的存在，修前连编译都过不去——
这与「防线整体缺席」同形，故先取前两条的行为红，再补后三条的结构红，两轮都要留证。

另有两条接线负控（`RepairModelEvidenceTest`），修前红、修后绿：

| 用例 | 修前失败摘要 |
|---|---|
| `RepairModelEvidenceTest.界面不得把零候选合成读取失败` | 修前 `RepairActivity` 正是 `if (connections.isEmpty()) UiText.t(this, "未读到可用模型…")` |
| `RepairModelEvidenceTest.发送键跟随 sendEnabled 而不是候选数` | 修前 `send.isEnabled = notice.modelControlsEnabled` 且两处 `= connections.isNotEmpty()` |

## 自查抓到的一个实现缺陷（值得记）

第一版把 `rootMissing` 传进 `present()` 就以为完事，但 `RepairActivity` 仍在 worker 里
`if (connections.isEmpty()) modelFailure = "未读到可用模型…"`。而 `failure != null` 是最高优先级分支，
于是根缺失分支永远轮不到——**修了数据层、也修了文案表，用户看到的仍是那句话**。
单测当时全绿（`present()` 的行为对），红的是接线。所以判据不能只钉纯函数，还要钉
「Activity 不得自己合成结论」；两条接线负控就是为此留下的。
