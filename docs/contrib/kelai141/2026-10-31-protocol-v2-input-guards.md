# 协议/分页/完整性闸三处输入判据加固（#1208 / #1209 / #1210）

## 现象

三条 issue 都指向同一类形态：**判据落在折算后的数值或"非空字符串"上，而不是落在类型与形状上**。

- #1208：`n` 走 `Number(d.n)`，`null`/`''`/`false`/`[]` 全折算成 0 ⇒ 「n 缺失或类型错」被当成空树放行，
  而空树分支在列校验之前提前返回，于是 86 行的载荷能解成空树并报 `ok:true`。
  同一函数的 `origRow` 是 `Int32Array`，句柄域越过 2^31 会被截断成负数（3000000000 → -1294967296），
  截断后的「上一项」还让严格递增判据失效（0 与 4294967296 都成 0）。
- #1209：`pageRows` 只夹下界，`offset >= rows.length` 时产出倒挂区间（文案印「第 100..99 行」）并把
  `omitted` 算成 0 —— 「页外还有 100 行」这一事实被抹掉；`Infinity`（`Number('1e999')`）还会序列化成
  `null`，违反工具声明的 `type:'number'`。
- #1210：完整性闸只校验 `bounds` 是**非空字符串**，不校验它能被解析；两个解析器要求精确
  `[d,d][d,d]`，偏差即返回 null，下游 `parseBounds` 拿到 null 就 `continue` ⇒ **闸报 OK 的同时可以
  100% 丢节点**。

## 真因

判据与它所依赖的事实之间隔了一层**宽松转换**（`Number()`、`Math.max` 只有一侧、`typeof === 'string'`）。
"值能被转成合法数字"不等于"调用方给了合法数字"；"字符串非空"不等于"字符串可解析"。

## 修法

- `n` 的判据改落在 `typeof` 上（`typeof nRaw !== 'number' || !Number.isInteger(nRaw) || nRaw < 0`），
  一次堵住 null / '' / false / [] / "0" / true 的全部折算入口；
- `rawCount > 2 ** 31` 直接失败关闭，让 Int32 截断在入口就不可能发生；
- `pageRows` 同时夹上下界，并把非有限 offset 收敛成 0；
- 完整性闸新增**只判形状**的 `BOUNDS_SHAPE` 判据（`^-?\d+` 形式），不复用 `parseBounds`
  ——后者对合法的零尺寸 `[0,0][0,0]` 也返回 null，复用会把合法骨架节点判成坏。

## 一处刻意不采纳 issue 的建议

#1208 的 issue 给了备选 B：「`n=0` 时也校验各列为空数组」。**没有采纳**：B 只在「n 被折算成 0」时
才有意义，而类型判据已经把折算入口关死；剩下的 `n=0` 只可能是调用方真的声明空树，列内容与产物无关。
实测 B 会把现有输入契约 fuzz 用例（240 例里必须至少有一例被接受）打红——那是「别把合法载荷一并否掉」
的红线，故只做 A。
