# 平板原生启动页与开屏视频铺满（#1320）

## 现象与真因

原生启动页也受影响：`GuideChrome` 在每次布局变化后，把内容、底部操作区和管理宿主压回 `ds_guide_max_width=440dp`。
平板横屏实读 2800px 宽，品牌与状态卡仍只占中间 1100px；背景虽已全屏，原生 UI 本身被限在手机列宽。
删除这层固定上限及退役资源，沿用原有 MATCH_PARENT。MainActivity 的系统栏与 24dp 外边距继续统一处理。
`GuideViewportDeviceTest` 测量真实 View 树，覆盖手机、平板、连续横竖屏尺寸变化，并执行第二轮布局以捕获布局回调中的再次限宽。

当前源码已有 `SplashOverlay`，通过 `TextureView + MediaPlayer` 播放用户导入的启动视频。
Issue 早期评论所述「本仓没有启动图实现」不适用于当前源码。

旧 `applyCover` 把 `max(viewWidth / videoWidth, viewHeight / videoHeight)` 同时用作两个轴的矩阵缩放。
该缩放率适用于视频像素，但 `TextureView.setTransform` 操作的是 View 矩形；视频内容此前已经被映射到 View 尺寸。
因此，相同比例的 3840×2160 视频在 1600×900 View 上也会被再次缩至 0.4167 倍，露出背景；不同宽高比时还会变形。

## 修法

原生 UI 随宿主可用宽度展开；不按比例放大字体和按钮高度。既有静态用例从要求引用旧上限更新为禁止恢复已退役上限，实际宽度由设备测试断言。

`SplashPolicy.coverTransform` 先计算等比铺满后的目标视频矩形，再除以 View 宽、高，得到两个 View 轴的缩放率。
`SplashOverlay` 使用这一矩阵，媒体尺寸就绪及纹理尺寸变化时均重算，平板横竖屏共用相同路径。
无尺寸时等待下一次回调，避免产生无效矩阵。播放、静音、超时与退出行为沿用既有流程。
