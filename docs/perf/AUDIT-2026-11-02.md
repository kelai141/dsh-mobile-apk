## 1. 度量纪律与证据分级

本轮没有设备，所以一切都必须在宿主侧落地成可复现的数字。为避免自欺，采用三级证据：

| 级别 | 类型 | 是否受 CPU 抖动影响 | 本报告用途 |
|---|---|---|---|
| **A 级** | 字节数、文件数、条目数、sha256、代码行数、调用点数 | **不受影响** | 主证据 |
| **B 级** | 同一输入下的 A/B 变体差分（如 剥载荷 vs 原文件 的 gzip 差） | 弱影响（同机同轮） | 收益量级 |
| **C 级** | 绝对墙钟时间 | **强影响** | 只用于同轮内相对排序，绝不跨轮比较 |

**本轮踩到的实测教训（写下来，因为它直接影响了结论可信度）**：多个审计 agent 并发跑 CPU 密集任务时，同一个 xz 解码从 19.4 s 漂到 39.1 s（2.0x）。**任何小于 2x 的绝对时间差异在本轮环境下都不可信**。因此本报告的收益结论一律优先用 A/B 级证据；凡只能给 C 级的，都显式标注「宿主并发负载下测得」。

### 一个具体的自我纠正（示范口径）

我最初测出「`File.getCanonicalPath()` 逐条目调用 = 134.6 s」——那是在 **Windows/NTFS** 上测的。改到 **WSL/ext4**（与 Android 同为 Linux，同为 `realpath(3)`）复测得 **1.70 s**（45,585 条目），缓存唯一父目录后 0.25 s。**差 79 倍。** 若不做这次复测，就会把一个 1.7 s 的项误报成 134 s 的「重大发现」。

## 2. 必须纠正的三条（防止后续走弯路）

### 纠正 1：`-Fast` 档的 preset 1 是设计行为，不是缺陷 —— **不要「修复」它**

A 块报告 A-2 称「出厂归档是 preset 1 产物，换回 -6 可省 32.72 MiB（17.1%）」。这条**必须作废**，理由在源码里：

```
scripts/build-apk-013.ps1:15-18
  if ($Fast) {
    if (-not $OnlyAbi) { $OnlyAbi = 'x86_64' }
    $env:DSH_INJECT_PRESET = '1'
    Write-Host "== Fast 档：OnlyAbi=$OnlyAbi，DSH_INJECT_PRESET=1（产物体积增大，禁止用于发布资产）=="
```

```
scripts/inject-all.py:8,155
  发布档 preset 由 DSH_INJECT_PRESET 控制（默认 9 保发布保真）
  preset = int(os.environ.get("DSH_INJECT_PRESET", "9"))
```

即：**preset 1 是 `-Fast` 档刻意的取舍**（注释：注入链压缩 380 s → 75 s/遍），且脚本自己在输出里写着「禁止用于发布资产」；**发布路径默认 preset 9**。

A 块用 `xz -1 -T1` 逐字节复现了 200,877,488 B / sha256 相同 —— 这确实是**优秀的方法学**（它证明了产物的身份），但**结论方向反了**：它证明的是「磁盘上这份 assets/snapshot.tar.xz 是一次 Fast 构建的残留」，**不是「发布包被压坏了」**。

**处置**：任何「把 preset 提到 6/9 以减小体积」的改动都**不成立**（发布路径本来就是 9）。这条同时解释了为什么 `app/src/main/assets/snapshot.tar.xz`(191.57 MiB) 与 `snapshot/snapshot-x86_64.tar.xz`(142.29 MiB) 差这么多：前者是 Fast 档注入产物，后者是另一档/另一代引擎的产物。

### 纠正 2：`out/v0.14.9` 的 APK 不能当体积基线

它内嵌 157,861,552 B 旧快照，而当前 assets 是 200,877,488 B。拿它算「snapshot 占 APK 96.77%」这一**比例**是有效的，但**绝对体积基线无效**。

### 纠正 3：日常冷启动没有解压，别在它身上算解压账

`EngineStartFlow.kt` 的路径是 `if (!snapshotFresh()) refreshSnapshot(...)`，`snapshotFresh()` 常态只需 1 次 `readText`（64 字符指纹）+ 1 次 `stat`。**日常冷启动的快照成本是 5-8 次文件系统调用**。
解压只在三种情况付：① 首装；② 覆盖安装（内嵌指纹变）；③ 运行时树被改坏。**且它跑在后台线程，不阻塞首帧。**

同理，全量 SHA-256 预检（`bundledAssetDigestProblem`，200.88 MB / 宿主 median 1304.3 ms / 146.9 MB/s）也**只在刷新时付**，不计入日常冷启动。

### 3.3 解压成本拆分（WSL/ext4，单线程，与 Android 同为 Linux）

| 场景 | 墙钟 |
|---|---:|
| 纯 xz 解码、零写盘（CPU 地板） | **19.43 / 19.91 s** |
| tar 列表（解码 + 解析 53k 头） | 25.27 s |
| 真实解压（建 44,568 文件 + 写 715.67 MiB） | 25.20 / 27.69 s |
| Android 专有 per-file 开销（1× unlink-miss + 4× chmod × 44,568） | chmod 1,161 ms + unlink 714 ms = **1.9 s（~7%）** |
| 逐条目 `realpath`（`resolveEntry` 现值），缓存唯一父目录后 | **1.70 s → 0.25 s** |

**结论：解压时间 ≈ xz 解码 CPU。** IO 与元数据操作合计上界约 9%（1.9 s + 1.7 s / 26 s）。这直接否掉「改流式写 / 合并 chmod / 缓存 canonicalPath」这类直觉方案——它们是 7-9% 的量级，却要动 L2 快照事务面。

### 3.4 归档是单块流（否决「并行解码」整条路线）

```
$ xz --list --verbose app/src/main/assets/snapshot.tar.xz
Streams:           1
Blocks:            1          <-- 单块
Compressed size:   191.6 MiB (200877488 B)
Uncompressed size: 767.0 MiB (804229120 B)
Ratio:             0.250
```

xz 只在单线程或数据小于块大小时产出单块。而构建器 `build-snapshot-013.mjs:1404` 明明用的是 `xz -T${XZ_THREADS} -6`（XZ_THREADS=8）。原因是下游 `inject-snapshot.py:70-71` 把归档整读进内存，第 123 行用 `lzma.open(dst,"wb",preset=...)` **重新压缩**。

**这条的意义是「否决」而非「优化」**：单块流 ⇒ 设备上无论换什么解码器（含 xz-utils 多线程解码）都拿不到并行度。我在 WSL 实测同一份输入：`-T1` 19.4 s vs `-T8` 23.5 s（且并发负载下不可信）——**同一流的多线程解码几乎无收益**，因为只有 1 块。

| **D1-3** | 「复制引擎日志」`copyGuideLog → readEngineLogFull → f.readText()` 是**无上限整文件读且在主线程**；同文件已有 `mirrorLogBounded`(2 MB 有界) 未被复用 | 消除一条无上限 ANR 路径 | 低 |
| **D2-1** | 解压峰值：stage 716 MiB + previous 树同时在场 ≈ **1.5 GB**；**解压前无 `StatFs` 前置检查**（唯一空间检查在 swap，跑在解压之后） | 消除「解压到一半 ENOSPC」 | 中 |
| **D3-3** | `check-snapshot-secrets` 在真实注入产物上判红：cmake 自带**真实 PKCS#12 容器** `Windows_TemporaryKey.pfx`（2,560 B，ASN.1 头已核） | 合规（体积可忽略） | 中 |

**负控**：`audit-append-io.mjs` 三形态对照（A open+write+close / B 常驻句柄 / C +fsync）：A=274.2 us，B=24.5 us（**11.2x**），C=288.2 us（仅 +5%）——同时证明「当前形态白付 11 倍却没有换来耐久性」。

## 5. Top 5（建议第二阶段做这五条）

排序口径：**收益量级 ÷ 改动风险**，并优先选「A 级证据支撑、零用户可见行为变化」的。

### #1 剥掉 `dsh-client-ui-settings-account` 的 5.08 MB 内联 base64 位图

> **状态：排到最后再做（不是搁置）。**
> 执行顺序（用户 2026-11-02 拍板）：`#4` → `#5` → `#2` → **最后回头做 #1**。
>
> **动手前必须先回答三个问题，答不上来就写「不做」并给理由，不得为减体积硬拆：**
> 1. **那 5.08 MB 到底是什么**——哪个包、哪些图标、base64 内联的是什么格式（PNG/SVG/多倍图）、
>    为何要内联（离线可用？单文件分发？上游打包方式？）。
> 2. **能不能外链/懒加载**——若设置页图标必须首屏可见，至少可改外链静态资源或按需解码。
> 3. **改完怎么证明没影响**——给一份「图标清单前后对比」（数量、尺寸、显示位置），拿不到就放弃。
>
> **收益类型存疑（需先证伪再动手）**：首屏传输在本地回环上（引擎与 WebView 同机），
> 5 MiB 的 gzip 省下来的主要不是网络时间，而是**引擎每次响应现压的 CPU**（B-4 实测该包单压 718 ms）
> 与 V8 解析（6.2 ms）。这两项的量级需要在设备上复核后才值得动上游补丁面。

> **调查已完成（2026-11-03）：结论「不做」。详见 `#1-INVESTIGATION-2026-11-03.md`。**
>
> 三问的答案与本节的原有估算**不一致，以下以调查为准**：
>
> 1. **不是设置页图标，是 onboarding 引导页插画**：8 张 WebP（最大 3993x2480，约 990 万像素）
>    占 2,400,254 B（99.7%），7 张 SVG 图标合计仅 6,349 B。原任务里「设置页图标必须照常显示」
>    这条约束**不适用** —— 剥掉不碰任何设置页图标。
> 2. **引擎根本没开 gzip**：`dsh-host-webserver` 的 `DEFAULT_COMPRESSION = "none"`，
>    全快照无人设为 gzip（`engine-overlay.json` 里的 `compression` 是 npm 依赖版本号）。
>    我复现的 gzip 成本是 **87.9 ms（sync）/ 95.3 ms（stream）**，**不是 718 ms**。
>    => **「省引擎 gzip CPU」这条收益不存在。**
> 3. **真实可省的是**：base64 解码 5.4 ms（一次性）、V8 解析测不出（<1 ms）、
>    首屏 raw **-2.29 MiB**（走本机回环，且 `IMMUTABLE_CACHE` 一年缓存 => 只有首次安装后第一次启动付）。
>
> **不做的理由**：收益前提被证伪 + 唯一真实收益只覆盖「首装首启」而本轮主题是冷启动 +
> 改动面（上游补丁 + 逐字节镜像 + 每次 bump 重做）与收益不成比例 + 8 种组合的插画正确性无设备可验。
>
> **本节下方「收益/预估收益」的 718 ms 与「决定性量级」判断已被推翻，保留原文仅为留痕。**

- **收益**：首屏 gzip **-2.42~-3.62 MiB（-46%~-71%）**；引擎单次 gzip CPU -0.2~0.7 s；渲染进程峰值内存风险 -75.6 MiB（推导，需设备复核）。**这是本轮唯一的「决定性」量级收益。**
- **风险**：中。上游包，需走 `scripts/patches/` 运行时补丁面（本仓已有同类补丁如 `image-expiry-E1.mjs`），会打破 `check-patch-mirror.mjs` 逐字节镜像 ⇒ 铁律 6 双仓同步，且每次上游 bump 需重做。
- **工作量**：M
- **备注**：**必须先确认图片改成静态路由后离线仍可用**（onboarding 在引擎起来后才渲染，可接受）。这一条建议先做 PoC 量一下真实收益再决定是否落地。

### #2 `audit.ndjson` 改正上有界写
- **收益**：单条 IO **-91%**（11.2x 负控确证）；消除全仓唯一无上限状态文件（推导年 ~106 MB @1000 条/天）。
- **风险**：低（形态改动），但属 L2 取证面 ⇒ 需即时三层或等价负控。
- **工作量**：S
- **备注**：这是同一套「有界写」纪律里唯一漏掉的落点，其余 23 个落点都已覆盖。补齐后取证面反而更完整。

### #3 `check-gate-skips` 缩小探针面
- **收益**：构建链 **-140~-190 s/次**（占现墙钟 80.7%）。
- **风险**：低。但**必须避免「把判据改小来借绿」**——缩小探针面的同时要在 `--list` 里显式登记「哪些文件属于审计面」，否则就是把门禁的覆盖面悄悄砍掉。
- **工作量**：M

### #4 三处后台轮询加 `document.hidden` 门
- **收益**：后台唤醒 **135 次/分钟 → 0**（静态上界）。参照实现已在 `native-browser-auto-place.ts:87-101`。
- **风险**：低（只影响后台排不排下一拍）。
- **工作量**：S

### #5 `FileIncoming.sweepExpired` 移出 `onCreate` 主线程
- **收益**：消除唯一随用户使用量增长的主线程冷启成本（N×(stat+open+read+JSON.parse)，上界无硬限）。
