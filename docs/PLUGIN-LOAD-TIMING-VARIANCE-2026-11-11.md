# 插件加载耗时：单次测量不可用（2026-11-11）

## 背景

装插件后发现 `loader-settle-wait` 变长，初判「插件越多启动越慢」。做了一次 A/B，结论被数据推翻。

## 数据

设备 `emulator-5586`（API 35、x86_64），同一份 APK，每次重启后从 `engine.log` 读 `loader-settle-wait`。

| 插件数 | 观测值（秒） |
| --- | --- |
| 3 个（历史两次） | 52.6 / 95.7 |
| 6 个（一次） | 204.6 |
| **2 个（两次新测）** | **160.5 / 149.5** |

## 结论：假设不成立

**2 个插件比 3 个还慢**，两次复测都在 150–160 秒。插件数量与 `loader-settle-wait` 不是线性关系。

更关键的是**组内波动**：

- 同一配置（2 个插件）连续两次：160.5 / 149.5 秒，差 11 秒；
- 另一配置（3 个插件）历史两次：52.6 / 95.7 秒，差 43 秒。

组内波动接近甚至超过组间差异。**单次测量在这台设备上没有判别力。**

## 仍然成立的事实

- 6 个插件时 `loader-settle-wait` 到过 204.6 秒，超过壳侧启动预算，触发 `boot-budget-exceeded`，
  应用停在失败页需要点「Retry startup」。这是**真实发生的**，但不是插件数量的线性后果。
- 组合条目数随插件增加（`records` 64 → 79），这一点是确定的；它不是耗时主因。

## 教训

本项目已经在测量上栽过多次（装错二进制两次、探测失败两次）。这次是不同的坑：**测量本身波动太大**。

做性能对比的最低要求（本设备不满足）：

1. 每个配置至少 5 次，取 p50 与范围，而不是单次；
2. 记录当时的系统负载与上一次启动的间隔；
3. 组内先稳定（同一配置重复到范围收敛）再换配置；
4. 换设备复现一次，排除设备特有行为。

**这台 AVD 不适合做精细性能对比。** 插件加载性能的结论需要生产设备或受控环境。
